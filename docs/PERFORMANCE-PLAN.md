## 可用工具与取舍

| 工具/方法 | 用在本项目哪里 | 选择 |
| --- | --- | --- |
| [Playwright 自动等待](https://playwright.dev/docs/actionability) | 用现有隔离扩展测试比较旧版/新版正确性与耗时，借鉴条件就绪后继续、断言重试 | 已是项目开发依赖，优先使用；无需再安装另一套自动化框架。它不是装进用户插件后就自动提速的模块 |
| [Puppeteer Locator](https://pptr.dev/guides/page-interactions) | 参考元素就绪和连续两帧位置稳定的判断方式 | 作为实现参考，不额外引入与 Playwright 重叠的依赖；位置稳定不能证明表单值已被业务状态接受 |
| [Testing Library waitFor](https://testing-library.com/docs/dom-testing-library/api-async/) | 参考立即检查、DOM 变化触发重查、轮询与超时兜底 | 在扩展内实现小型条件等待，不打包整个测试库。DOM 观察不到的 value 属性变化仍需事件/轮询回读 |
| [Chrome DevTools Performance](https://developer.chrome.com/docs/devtools/performance/reference) | 区分 JS 扫描、布局、网络等待、计时器空等；受控 CPU/网络减速测试 | 开发诊断工具，避免凭总耗时猜测全部瓶颈 |

Playwright 官方[明确不推荐固定超时等待](https://playwright.dev/docs/api/class-page#page-wait-for-timeout)。Chrome 官方也建议 [MutationObserver 只观察相关变化](https://developer.chrome.com/docs/extensions/get-started/tutorial/scripts-on-every-tab)，防止整页监听本身拖慢网页。

## 建议实施顺序

1. **下拉和日历先改条件等待。** 先检测所属弹层、可见唯一候选或目标面板是否已就绪；就绪即继续，未就绪再等待。点击后检查目标值、控件仍存在、正确弹层已关闭，保留有界超时和取消。搜索候选变化与级联选择按依赖串行，不对所有控件统一 `Promise.all`。
2. **普通文本合并等待。** 对已确认独立、没有联动的文本字段，依次赋值与发送事件，合并延迟回读；不要让几十项各自串行等待 100+120 ms。失焦触发重建或联动的字段仍设等待边界；DOM 节点被替换必须重新定位，不能算成功。
3. **控件识别只重算变化区块。** 一轮内缓存标签和区块信息；新增/删除记录、条件展开、节点替换时失效。缓存命中仍校验连接状态、区域归属和语义，不能复用陈旧行号。
4. **保留最终核验。** 先比较前述三项收益，再评估按字段最后变更时间调度延迟观察，使观察时间与后续填写重叠。对于长延迟回退，短暂不变化不等于真正提交；不得直接删除 5 秒观察来报告加速。

仅举算术上限：保留的 12 次下拉，各有 350 ms 固定等待，总预算 4.2 秒；如果能够用可靠状态检查替代，才可能回收其中一部分。其余操作也有类似机会，但由于日志截断与真实异步耗时，当前不承诺整页达到 5 秒、10 秒或某个加速倍数。

## 对比与稳定性验收

- 固定相同浏览器、源码版本、模拟资料、初始 0/1 行和冷/热候选状态；旧版与候选版交替运行，普通条件与受控延迟条件分别统计。
- 先在隔离夹具覆盖候选延迟、迟到回写、回退、节点重建、范围起止关联、错层、停止、重复运行；必要时增加样本，报告样本量、中位数、较慢尾部与失败类型，不仅选择最快一次。
- 表单最终目标值、记录数、已有内容保护、日期成对保持及错误报告全部一致后，再做快手新空白页实测。实页固定演示身份证仍必须报告拒绝，不能为提高成功率隐藏校验。
- 真实表单不自动保存/提交，不为跑基准清空用户页面。上传另计，不把人工文件选择时间混入插件写入阶段。
- 只记录控件类型、耗时和原因，不记录资料值。未来性能摘要应独立聚合，避免被事件容量截断；未采到完整数据时明确标为局部样本。
